## 1. Critical Bugs and Risks

### 1.1. `_extract_expected_json_keys` Function
**Risk**: The function uses a regex pattern `r"lyrics to fix:\s*\((\d+)\s*segments?\)"` to extract the number of lyric segments. However, this pattern is fragile and may fail if:
- The text contains variations like "lyrics to fix: (5 segments)" (missing space after colon)
- The word "segment" is pluralized differently (e.g., "segments" vs "segment")
- There are extra spaces or punctuation

**Impact**: If the regex fails to match, the function falls back to other heuristics, but if those also fail, it returns an empty list. This could cause downstream JSON validation to incorrectly expect no keys, leading to silent data loss or incorrect parsing.

**Recommendation**: 
- Make the regex more robust by allowing optional spaces and handling pluralization.
- Add unit tests for various input formats.
- Consider logging a warning when falling back to less reliable heuristics.

### 1.2. `_enforce_value_quotes` Function
**Risk**: The function attempts to wrap string values in escaped quotes (`\"value\"`) but does not handle:
- Strings that already contain escaped quotes internally (e.g., `"He said \\\"hello\\\"")` → could become `"\\\"He said \\\\\\\"hello\\\\\\\"\\\""` which is invalid.
- Non-string values (though it has a type check, it returns early for non-strings, which is correct).
- Multiline strings where internal newlines should be preserved but external quoting added.

**Impact**: Corrupted JSON output that fails to parse, especially when the LLM returns values with internal quotes or special characters.

**Recommendation**:
- Use `json.dumps()` for proper string escaping instead of manual quote handling.
- Only apply quoting if the value is a plain string without existing JSON encoding.
- Add comprehensive tests for edge cases involving quotes, escapes, and newlines.

### 1.3. `_strip_code_fences` Function
**Risk**: The regex `r"```(?:json)?\s*([\s\S]*?)\s*```"` is greedy in the wrong way due to the `.*?` being inside a group that allows `\s*` before and after. This can cause:
- Over-matching if there are multiple code fences in the text.
- Incorrect extraction if the content itself contains triple backticks.

**Example**: 
```
Some text
```json
{ "key": "value" }
```
More text
``` 
``` 
```
```
This could match from the first ``` to the last ```, capturing too much.

**Impact**: Extraction of incorrect or overly broad content, leading to JSON parsing errors.

**Recommendation**:
- Use a more precise pattern: `r"```(?:json)?\n([\s\S]*?)\n```"` to require newlines after opening and before closing fences.
- Or better, split on ``` and take the second block if it starts with 'json' or is plain.
- Add tests for multiple code fences and nested-like structures.

### 1.4. `_resolve_llm_runtime_kwargs` Function
**Risk**: The function uses `source.get("reset_context", config.DEFAULT_LLM_STATELESS)` and wraps it in `bool()`. However, if the source provides a string like `"false"`, `bool("false")` is `True`, which is incorrect.

**Impact**: LLM context reset behavior may be inverted when configuration comes from string sources (e.g., JSON config, UI inputs).

**Recommendation**:
- Use explicit truthy/falsy conversion: `str(source.get("reset_context", config.DEFAULT_LLM_STATELESS)).lower() in ("true", "1", "yes")`
- Or use a utility function for consistent boolean parsing.
